# AI Grid harm-exposure policies and connector metadata

Original observations: 6 October 2026. Implementation reassessment: 12 October 2026. Scope: current local working tree, including existing uncommitted changes. Static code and policy-package review, not a live tenant/database audit. “Collected” below means an implemented connector path, conditional on provider permissions, configuration, successful calls, and available provider fields. It does not establish that a particular tenant has fresh evidence or that a package is distributed/enabled.

## Conclusion

Use the existing AI_POSTURE and AI_EXPOSURE categories. Many proposed controls already have packages; prioritize completing their evidence paths over creating duplicate policies. New policies alone are sufficient only where retained metadata is already normalized into the required facts. Cross-resource harm paths require correlation support. Configuration findings establish weaknesses or potential exposure, not successful exploitation.

The October 6 inspected catalog contains 168 unique policy IDs across AWS, Azure, runtime, and cross-system exposure packages. The exposure evaluator has six concrete R2 handlers; the October 6 business-logic-guide description of three has now been corrected. No inspected AGCF package maps to LLM08; that is a mapping gap, not proof that retrieval controls are absent.

Status labels:

- **Reuse:** existing policy and relevant connector/fact path exist; verify tenant evidence and policy scope.
- **Derive:** relevant metadata exists, but a new normalized fact, comparison, or policy binding is needed.
- **Extend:** connector collection, safe field contract, or qualified external evidence is needed.
- **Correlate:** join multiple facts/relationships; extend or reuse an exposure handler.
- **External evidence:** not established by current control-plane metadata.

Candidate labels H01–H22 are planning references, not new registered policy IDs.

### Cross-provider evidence contract to add

These are proposed logical fields, not claims that they are already collected or that specific provider APIs expose them. Exact implementation names should follow the existing field registry. Each value needs provider/source, assessed artifact/version, observation time, completeness and evidence class.

| Contract | Required safe metadata | Applies to |
|---|---|---|
| Input influence | Source ID, source kind, writer/ingester trust class, effective write scope, approval baseline, agent-source relationship | AWS KB/S3; Azure Search/backing stores; Copilot knowledge sources |
| Effective action authority | Tool/action ID, READ/WRITE/DELETE/SEND/EXECUTE category, execution principal, effective resource scope, restrictions and approved matrix | AWS IAM/Lambda/AgentCore; Azure identity/tools; Copilot connections/actions |
| Approval control | Action ID, required-by-baseline flag, observed configured control, enforcement scope, evidence completeness | All three; application controls may require an external producer |
| Destination boundary | Tool/action ID, approved destination class/list reference, observed effective restriction, exceptions, scope | All three; distinguish network restrictions from business-level recipient controls |
| Retrieval isolation | Source/index ID, requester identity propagation, ACL/tenant-filter configuration and evidence scope | All three, with provider-specific applicability |
| Approval-relative integrity | Component identity, current and approved digest, algorithm/key compatibility, approval time, comparison result | All three; raw bodies remain excluded |
| Memory/handoff | Typed resource or peer edge, tenant/session/identity scope, permitted writers/delegation, retention and controls | Only where the workload has the capability; otherwise NOT_APPLICABLE |
| Controlled validation | System/deployment version, suite/case version, scoped authorization reference, attempt/outcome, oracle/evidence reference | All three; separate from raw runtime telemetry and rule-precision governance |

Implementation order within each connector is collect/derive → safe storage contract → typed fact producer → policy/provider scope → completeness/freshness gate → verification with representative sanitized evidence. Reusing the shared engine does not remove these provider-specific steps.

## Important end-to-end gaps

The metadata path is: provider response → collector projection → sanitizer/field contract → persisted snapshot → fact producer → policy requirements/evaluator → governed release → tenant assessment.

1. Representative Phase 2 fields (`effectiveAccessExceedsApprovedMatrix`, `permissionFilteringConfigured`, `documentAuthorizationConfigured`, `tenantPartitioningConfigured`, `azureMlOutboundEgressRestricted`, `datasetChangedAfterApproval`) have fact mappings but no connector population found in production source. They are also not present in `AiSecurityFieldContract.PUBLIC_METADATA`/`STORAGE_ONLY`. Adding only JSON policies will not make these fields usable.
2. AWS emits `permissionBoundaryState` and `effectiveAccessEvidenceComplete`, but these are absent from the inspected field allowlist. `permissionBoundaryAttached` is allowed. Even an emitted completeness flag would not independently prove correct effective-IAM evaluation.
3. AWS retained IAM wildcard-resource, PassRole, NotAction/NotResource, boundary, cross-account trust and trust-condition fields now have narrowly named configuration facts. They do not establish effective authorization.
4. A configured hostname, filter count, private endpoint, or source type must not be promoted into a stronger trust, effectiveness, egress, or attacker-influence claim.
5. Successful static source inspection does not verify tenant collection coverage, published policy state, or production evidence freshness. Those require a tenant scan/assessment audit.
